## Introduction
Jumping into ICS 314, I had a rough idea of what concepts and coursework to expect from the syllabus. However, I did not fully understand how those different aspects would come together throughout this course. Slowly but surely, I began to see that developing software involves not only creating a working application, but also determining how a team should approach its work, how software should be structured, and what responsibilities developers have toward the people who use it. Concepts such as agile project management, design patterns, and ethics in software engineering particularly helped me develop this broader understanding. In this essay, I plan to go more in-depth about these concepts and how they not only apply to web development but also extend to software engineering as a whole.

## Agile Project Management
Agile Project Management is an approach to software development that emphasizes iterative development, collaboration, and adapting to changing requirements rather than attempting to plan and complete an entire project at once. Working through the group project, I experienced this approach through Issue Driven Project Management, where development work was organized around individual issues representing features, bugs, or other tasks that needed to be addressed. These issues provided a way to break a larger project into smaller and more manageable pieces of work while also giving team members a clear understanding of what needed to be completed. As development progressed, issues could be created, assigned, prioritized, and closed as the needs of the project changed. Problems eventually arose, making the seemingly smooth path bumpier yet still manageable. This allowed the development process to remain flexible rather than requiring the team to follow a fixed plan from beginning to end.

Through this experience, I got a proper understanding of how agile project management extends beyond web application development and how software projects rarely follow a perfectly predictable path. For instance, a cybersecurity team developing a vulnerability detection tool could use Issue Driven Project Management to organize tasks such as implementing detection methods, addressing vulnerabilities, improving logging, and testing the system. As new vulnerabilities or requirements are discovered, they could be added as new issues and prioritized accordingly, further showing how flexible the development process truly is, especially in a larger context.

## Design Patterns
Another concept that expanded my understanding of software engineering was design patterns. Design patterns are established, reusable approaches to common problems that arise when designing software. Rather than providing a piece of code that can simply be copied into a project, a design pattern provides a general structure for solving a particular design problem. The value of design patterns comes from providing developers with a common way to think about and communicate solutions to recurring problems. They can help make software more organized, maintainable, and easier for other developers to understand. While not explicitly clear, I did stumble across design patterns while working through each experience in ICS 314. One such case was pieces throughout assignments that I could utilize in my final project. Fr example, I encountered recurring approaches for displaying data through cards or tables, using forms to add or edit existing data, and providing functionality for deleting data. As I incorporated these approaches into my own project, I began to see that developers do not necessarily need to design every feature from scratch when similar problems have already been solved through established patterns.

More importantly, this concept extends beyond web development and applies to software engineering more broadly. For example, a system that manages employee information, a desktop inventory application, or a cybersecurity tool may all need ways to display information, modify existing records, or remove outdated data. Although the specific interface may differ, the underlying design problem remains similar. This showed me that design patterns are valuable not because they provide a solution for one particular type of application, but because they give software engineers reusable ways to approach problems that occur across different projects.

## Ethics in Software Engineering
The final concept I chose to reflect on is ethics in software engineering. Software engineering ethics involves considering the responsibilities and consequences associated with developing and deploying software, rather than focusing solely on whether a system functions as intended. A technically successful application can still create problems if it compromises user privacy, introduces security vulnerabilities, treats users unfairly, or is used in ways that cause harm. This makes ethics an important part of software engineering because developers have to consider not only what their software can do, but also how it should be designed and used. Working with the course’s emphasis on AI-assisted software development also made me think more about the responsibility developers have when using AI tools. While tools such as ChatGPT and GitHub Copilot can help developers work more efficiently, their output still needs to be evaluated by the developer. Generated code may contain bugs, security vulnerabilities, or approaches that the developer does not fully understand. As a result, developers cannot simply rely on AI-generated solutions without understanding or evaluating them, and they remain responsible for the software they choose to implement.

While these concerns are relevant even within web development, they become even more significant when software is used in areas such as healthcare, finance, cybersecurity, or artificial intelligence, where mistakes can have consequences beyond a malfunctioning application. Ultimately, ethics taught me that being a software engineer involves more than having the technical ability to create something. Developers also have a responsibility to consider how their decisions affect the people and systems that depend on their software.
